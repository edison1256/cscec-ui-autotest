# 测试用例生成器 UI 自动化适配器（Test Case Generator UI Adapter）

## 适配器边界

- 原始 `test-case-generator` 是稳定上游，只负责需求理解、测试大纲和详细黑盒用例生成。
- 本副本只做 UI 自动化适配：读取 `详细测试用例数据.json`，筛选 UI 自动化候选，输出资产登记片段。
- 不修改原始 `D:\AI\LM\.agents\skills\test-case-generator`。
- 不改变黑盒用例生成口径，不反向改写需求测试设计产物。
- UI 自动化资产流转规则见 `references/ui-automation-adapter.md`。
- 候选资产生成脚本见 `scripts/select_ui_assets.py`。

## 资源使用

- 生成阶段1输出前，先参考 `references/outline-template.md`，保持测试范围摘要、待确认项和大纲结构一致
- 生成阶段2输出前，先参考 `references/cases-template.md`，保持表头、字段命名和示例行一致
- 生成阶段2详细用例时，优先维护 `{需求文件夹}/详细测试用例数据.json`（可参考 `references/cases-data-template.json`），再运行 `scripts/gen_cases.py` 渲染 Markdown；不要为每个需求重复新建一次性 `generate_cases.py`
- 生成 `.xmind` 时优先使用 `scripts/gen_xmind.py`，不要依赖外部 XMind 工具作为主路径
- 生成 `.xlsx` 时优先使用 `scripts/gen_excel.py`，不要在 `SKILL.md` 中重复维护脚本内部格式细节

## 系统背景

- **平台全称**: 一体化资源平台（简称 IRP / 中建云 / 一体化）
- **知识库位置**: `已上线需求/` — 所有已发布生产的需求文档（.docx）
- **立项文档**: `立项/` — 平台建设方案、操作手册、设计文档
- **新需求位置**: 由参数指定，默认 `新需求/`
- **核心概念**: 租户(多级)、资源类型(应用/硬件/云产品/组件/数据资源)、规格套餐、审批流(可视化画布)、工单中心、评分细则（智能建造专属）

## 核心原则：基线先行，用例后行

> ⛔ **铁律：任何测试设计之前，必须先完成系统基线建立（阶段0）。**
>
> 新需求**从来不是孤立的**。不了解已有系统，测试用例就会：
> - 🔴 **遗漏回归场景** — 不知道哪些已有功能会被新改动影响
> - 🔴 **忽视数据兼容** — 不知道历史数据在新逻辑下是否会异常
> - 🔴 **忽略跨模块联动** — 不知道改动A会通过什么路径影响模块B/C/D
> - 🔴 **重复造轮子** — 不知道现有系统已有哪些能力可以复用/约束
>
> **如果阶段0被跳过或不充分，阶段1和阶段2的输出质量将大幅下降，必须回退重做。**

## 工作原则

### 边界清晰
- ❌ 不做产品功能的再设计或优化建议
- ❌ 不质疑需求的合理性或商业价值
- ✅ 仅基于既定需求设计测试用例

### 缺口标注
- 发现需求不明确/矛盾/边界未定义时，用 **【待确认：具体问题】** 标注
- 基于合理假设继续设计，假设处标注 **【假设：假设内容】**
- 样例数据标注 **【示例】**

### 质量优先
- 用例遵循 SMART 原则
- 覆盖：正向流程、逆向流程、边界条件、异常场景、数据一致性

## 执行流程（4个阶段）

### 阶段 0：系统基线建立 🔒 强制前置，不可跳过

> **门控规则**: 阶段0未完成前，禁止进入阶段1。判定完成的标准见下方"基线验证检查点"。

**目的**: 在设计任何测试用例之前，必须充分理解已有系统的功能基线，为后续的回归分析、兼容性验证、跨模块联动识别提供依据。

**步骤**:

1. **扫描知识库**
   ```
   Glob: 已上线需求/**/*.docx
   Glob: 立项/**/*.docx
   ```

2. **并行读取核心文档**（使用 Task 子任务并行，分3组）

   **第1组 - 资源/产品管理**：读取与资源管理、规格、产品编辑页相关的 .docx 文件
   **第2组 - 平台架构/最新迭代**：读取建设内容、操作手册、最新迭代需求文档
   **第3组 - 流程/工单/ITSM**：读取流程管理、工单中心、ITSM对接文档

   **读取 .docx 的方法**（重要！sandbox限制下的可靠方案）:
   ```bash
   unzip -p "文件路径.docx" word/document.xml
   ```
   然后从XML中提取 `<w:t>` 标签内的文本内容。

   ⚠️ **不要使用**:
   - `python -c "..."` — 可能被sandbox阻止
   - `pandoc` — 可能未安装
   - 直接 `Read` 工具读 .docx — 是二进制文件

3. **提取基线信息**（每份文档提取）:
   - 涉及的模块/功能
   - 关键业务规则
   - 角色与权限
   - 字段定义
   - 状态流转
   - 接口/API

4. **输出基线摘要**:汇总以下关键认知（必须覆盖，不可省略任何一项）
   - 控制台 vs 工作台 的区别与各自功能边界
   - 现有资源状态机（草稿→上架申请中→已上架→已下架→已停用）
   - 现有审批流程能力（提交/驳回/转签/加签/终止/撤回/催办）
   - 租户体系（多级租户、租户编码/名称/级别、租户与组织的关系）
   - 现有联系人字段（资源联系人、业务部门接口人、建设部门负责人等）及其当前必填/非必填状态
   - 工单分派逻辑（叶到根遍历、全局处理人兜底、应用角色分派）
   - 现有规格/套餐层级（后端类目→服务模式→属性项→规格→套餐）
   - 现有角色体系（平台管理员、应用管理员、应用运维、应用成员等）
   - 现有对外接口（ITSM集成、标签查产品等）
   - 历史数据迁移经验（已有的数据迁移规则和注意事项）

5. **🔑 基线验证检查点**（门控，必须全部通过才能进入阶段1）

   用 TodoWrite 创建检查清单，逐项确认：

   | # | 检查项 | 判定标准 |
   |---|--------|---------|
   | ✅1 | 知识库文档覆盖率 | 已读取 `已上线需求/` 和 `立项/` 中 ≥80% 的文档 |
   | ✅2 | 资源管理基线 | 能回答"现有编辑页有哪些Tab和字段？状态机有几种状态？" |
   | ✅3 | 审批流基线 | 能回答"现有审批流支持哪些操作？流程模板如何配置？" |
   | ✅4 | 租户体系基线 | 能回答"租户层级关系？租户与用户/组织的关联？" |
   | ✅5 | 工单体系基线 | 能回答"工单有哪些类型和状态？分派逻辑是什么？" |
   | ✅6 | 角色权限基线 | 能回答"现有哪些角色？各角色在各状态下可执行哪些操作？" |

   **如果任何检查项未通过**: 回到步骤2补充读取对应文档，不得跳过进入阶段1。

6. **🔗 新旧需求影响分析**（阶段0到阶段1的关键桥梁）

   读取新需求文档后，必须逐一回答以下问题（输出为表格，写入大纲文档）：

   | 分析维度 | 必须回答的问题 | 产出 |
   |---------|-------------|------|
   | **回归影响** | 新需求改动了哪些现有模块？改动可能破坏哪些已有功能？ | 回归测试清单 |
   | **数据兼容** | 现有数据在新逻辑下是否正常？是否需要数据迁移/默认值处理？ | 历史数据测试场景 |
   | **跨模块联动** | 新功能A的状态变化会通过什么路径影响模块B/C？ | 联动测试场景 |
   | **接口影响** | 对外接口的入参/出参/过滤逻辑是否变化？下游系统是否受影响？ | 接口兼容测试场景 |
   | **权限交叉** | 新增角色/权限与现有权限体系如何交叉？是否存在权限冲突？ | 权限组合测试场景 |
   | **状态机扩展** | 新增状态/流转是否与现有状态机冲突？边界状态如何处理？ | 状态机完整性测试 |

   **以上每个维度至少产出1条测试场景**，标注为"基线驱动场景"。这些场景必须体现在阶段1的大纲中。

   **示例**（以本次建造0415需求为例）：
   ```
   回归影响: R3把联系人改为非必填 → 现有上架校验是否受影响？现有工单分派逻辑是否兜底？
   数据兼容: R9接口变更 → 上线前历史数据是否默认"生效"？上线后新数据默认"未生效"？
   跨模块联动: R2租户选择 → 联动清空联系人 → 影响工单处理人分派
   接口影响: R9 → 建造项目组依赖的"标签查产品"接口过滤逻辑变更
   权限交叉: R10新增11个角色 → 编辑者角色与审批角色是否可兼任？自审自批？
   状态机扩展: R4新增"生效状态×审批状态"双状态机 → 与现有资源状态机如何衔接？
   ```

### 阶段 1：测试大纲输出（用于评审）

**前置条件**: 阶段0的基线验证检查点已全部通过 ✅，新旧需求影响分析已完成 ✅

**输入**: 新需求文档（同样用 `unzip -p` 读取 .docx）

**参考模板**: `references/outline-template.md`

**输出要求**:

1. **测试范围摘要**（表格形式）:
   - 涉及模块、改动类型、影响面
   - 涉及角色（新增/已有）
   - 关键业务规则（编号列出）
   - 主要风险（等级+说明）
   - **⭐ 与已有系统的交叉影响**（来自阶段0步骤6的影响分析）

2. **待确认问题列表**（按优先级P0→P2排序）:
   - 仅列影响测试设计的问题
   - 包含：编号、优先级、问题描述、影响模块、影响用例范围

3. **思维导图测试大纲**（Markdown树 + XMind文件）:
   - 层级：模块 → 场景 → 测试点维度 → 用例意图
   - 必须覆盖的维度（按适用性取舍）:
     - 主流程/关键路径
     - 分支流程/业务规则组合
     - 异常与失败处理（错误码/提示/回滚/幂等）
     - 字段校验与边界（必填/长度/格式/范围/枚举/跨字段）
     - 权限/角色/越权
     - 状态流转与一致性
     - 数据一致性与重复提交/并发
     - 性能/容量（如适用）
     - 安全/审计（如适用）
     - **⭐ 回归验证**（基线驱动，必选）— 新改动对已有功能的影响
     - **⭐ 历史数据兼容**（基线驱动，必选）— 升级后历史数据正确性
     - **⭐ 跨模块联动**（基线驱动，必选）— 改动A→影响B/C的传导路径
   - 叶子节点用"用例意图句式"：`X状态下提交Y，期望Z`

4. **用例量预估**（表格，总数控制在200以内）

**阶段1禁止项**: 不输出详细步骤表格；不编造缺失业务规则；必要时用【假设】标注。

**输出文件**:
- `{需求文件夹}/测试大纲.md`
- `{需求文件夹}/测试大纲.xmind`（优先使用 `py -3 scripts/gen_xmind.py --input "{需求文件夹}/测试大纲.md" --output "{需求文件夹}/测试大纲.xmind" --title "测试大纲"` 生成；若环境已配置 `python` 命令，也可用 `python scripts/gen_xmind.py ...`）

### 阶段 2：详细测试用例（用户确认大纲后执行）

**触发条件**: 用户回复"继续生成详细用例"或指定某些分支

**参考模板**: `references/cases-template.md`

**输出格式**（固定表头）:

| 所属模块 | 标题 | 类型 | 优先级 | 前置条件 | 负责人 | 步骤 | 预期结果 | 所涉及到的数据 |
|------|------|------|--------|----------|--------|------|----------|------------|

**字段规则**:
- **所属模块**: 从大纲模块名提取，格式如 `M1-控制台新增资源权限`
- **标题**: 用例编号+简述，如 `M1-01 应用管理"新增"按钮可见`
- **类型**: 从 功能/UI/接口/异常/权限/性能/兼容/安全/数据/回归 选（最多2个）
- **优先级**: P0/P1/P2
- **负责人**: `陈方达,周宇康`（除非用户提供名单）
- **步骤 / 预期结果**: 序号必须写成 `【1】`、`【2】`、`【3】` 这种格式，不得写 `1.`、`2.`
- **步骤 / 预期结果 / 前置条件**: 多行内容必须使用**真实换行符**保存，不得写 `<br>` 作为换行占位
- **所涉及到的数据**: 关键字段+样例值+边界值+数据构造要点，样例标注【示例】
- 依赖待确认项的用例，标题或前置条件标注【待确认】

**格式要求**:
- 为保证“步骤 / 预期结果 / 前置条件”列支持真实换行，详细用例文件优先输出为 **HTML table**（文件扩展名仍可为 `.md`）
- 表头字段名保持不变，仅输出形式从 GFM 表格切换为 HTML table
- Excel 导出脚本必须保留单元格内真实换行，不得把换行重新写回 `<br>`

**生成策略**:
- 使用 Task 子任务并行生成（按模块分组，2-3组并行）
- 每组子任务的 prompt 中需包含完整的系统基线上下文和需求细节
- 子任务完成后先汇总为结构化 JSON 数据文件 `{需求文件夹}/详细测试用例数据.json`，字段可参考 `references/cases-data-template.json`
- 使用公共脚本生成 Markdown，避免重复编写一次性生成脚本：
  ```bash
  py -3 scripts/gen_cases.py --json "{需求文件夹}/详细测试用例数据.json" --output "{需求文件夹}/详细测试用例.md"
  ```
- 仅当公共脚本无法表达特殊转换逻辑时，才允许临时脚本；临时脚本不得替代 `scripts/gen_cases.py` 作为常规路径

**输出文件**:
- `{需求文件夹}/详细测试用例数据.json`
- `{需求文件夹}/详细测试用例.md`

- `{需求文件夹}/详细测试用例.xlsx`

## 测试维度覆盖检查表

设计用例时，系统性检查以下维度：

| 维度 | 说明 | 示例 |
|------|------|------|
| 功能正确性 | 主流程、分支流程、业务规则 | 提交→审批→完成 |
| 边界值 | 最小/最大/临界/空值 | 输入0/1/999/空 |
| 异常处理 | 非法输入、网络异常、并发冲突 | 重复提交、超时 |
| 数据一致性 | 跨模块/跨页面数据同步 | 列表/详情/编辑/API 数据一致 |
| 权限控制 | 角色权限、越权操作 | 无权限调API返回403 |
| 状态流转 | 状态机完整性、非法转换阻止 | 审批中→不可编辑 |
| 前后端一致 | 前端校验+后端校验双重验证 | 绕过前端调接口 |
| 历史数据 | 升级兼容、数据迁移 | 历史记录不丢失 |

## 已知陷阱与优化建议（来自实战经验）

### .docx 文件读取
- ✅ 可靠方案: `unzip -p "path.docx" word/document.xml` → 提取XML文本
- ❌ 不可靠: Python脚本（可能被sandbox阻止）、pandoc（可能未安装）
- ⚠️ XML输出可能很大(40KB+)，会被截断保存到临时文件，需用 Read 工具读取

### 并行子任务管理
- ✅ 设置 `run_in_background=true`，最多3个并行
- ⚠️ 子任务可能超时（>5分钟），设置合理的 timeout（300000ms）
- ⚠️ 超时后直接在主线程补充完成，不要无限等待
- ✅ 每个子任务的 prompt 必须自包含，不能依赖主线程上下文

### Excel 生成
- ✅ 优先先运行 `py -3 scripts/gen_cases.py --json "{需求文件夹}/详细测试用例数据.json" --output "{需求文件夹}/详细测试用例.md"` 生成详细用例 Markdown
- ✅ 优先直接运行 `py -3 scripts/gen_excel.py`（或已配置 `python` 命令时运行 `python scripts/gen_excel.py`）
- ✅ 导出前先检查“步骤 / 预期结果 / 前置条件”列是否已使用真实换行，且序号是否为 `【1】` 格式
- ✅ 常规任务只维护 `详细测试用例数据.json`；不要在需求产物目录重复创建 `generate_cases.py`
- ⚠️ 模块名正则匹配：长前缀优先（M10 → M1 → M2...）
- ⚠️ Markdown表格解析：注意区分表头行、分隔行、数据行
- ⚠️ 如详细用例文件使用 HTML table，导出脚本需兼容 `<table><tr><td>...</td></tr></table>` 结构
- ⚠️ 汇总表/概览表的行要过滤掉，只保留用例数据行

### 用例设计
- 状态组合测试（如 生效状态×审批状态=4种组合）是高价值测试点
- 并发/幂等测试（重复提交、同时审批）是常见遗漏
- 越权测试（绕过前端直接调API）必须覆盖
- 联动清空（如切换租户→清空联系人）需验证数据完整性

## 参数说明

`$ARGUMENTS` — 新需求文件夹的相对路径（相对于vault根目录）

- 默认值: `新需求`
- 示例: `新需求`, `迭代需求/sprint-42`, `需求/2026Q2`

## 执行入口

收到参数后，按以下顺序执行：

1. 检查参数，确定新需求文件夹路径
2. 扫描新需求文件夹中的 .docx 文件
3. **🔒 执行阶段0（基线建立）** — 并行读取知识库全量文档
   - 输出基线摘要（10项认知）
   - 完成基线验证检查点（6项全通过）
   - ⛔ 若检查点未通过，补充读取，不得跳过
4. **🔗 执行新旧需求影响分析** — 6个维度逐一回答
   - 输出影响分析表格
   - 每个维度≥1条"基线驱动场景"
5. 执行阶段1（大纲输出）— 输出 .md + .xmind
   - 大纲中必须包含基线驱动的回归/兼容/联动场景
6. **⏸️ 暂停**，等待用户确认大纲
7. 用户确认后执行阶段2（详细用例）— 输出 .md
8. 自动执行阶段3（Excel导出）— 输出 .xlsx
9. 输出最终统计摘要

> **质量保证**: 如果最终的用例中完全没有"回归验证"、"历史数据兼容"、"跨模块联动"类型的用例，说明基线分析不充分，需回退到阶段0重新补充。
