# 生产控制台交互层级矩阵

本文档用于回答两个问题：生产控制台有哪些可验证交互，以及现有自动化实际走到了哪一层。
当前版本仅依据代码、pytest 收集结果、资产登记和既有文档进行静态盘点；未重新访问生产页面，也未修改业务测试。

- 盘点日期：2026-09-14
- 目标环境：PROD
- 控制台域名：`https://irp.cscec.com/`
- 租户口径：中建云
- 当前账号口径：以账号实际可见菜单为准，暂不把具体角色作为断言条件
- 生产选择器：`smoke and readonly`

## 1. 矩阵口径

### 1.1 交互层级

| 层级 | 定义 | 典型证据 |
| --- | --- | --- |
| L0 | 域名、认证、会话可用 | 登录成功，未跳回 IAM |
| L1 | 入口或页面外壳可见 | 菜单、标题、页面主容器可见 |
| L2 | 页面首层只读交互 | 搜索、筛选、分页、普通 Tab、展开收起 |
| L3 | 业务对象详情 | 点击列表行、详情、抽屉、编辑页只读回显 |
| L4 | 详情内部交互 | 详情 Tab、权限树、流程图、历史记录、嵌套页面 |
| L5 | 写操作前置探查 | 新增、删除、提交、申请等弹窗或确认页打开，但不确认 |
| L6 | 受控真实写入 | 只允许明确授权的测试数据与业务范围 |

层级记录的是单条路径实际达到的最高层级，不因同一模块的其他用例更深而自动提高。

### 1.2 入口类型

| 标记 | 含义 |
| --- | --- |
| UI | 从用户可见入口逐级点击 |
| DIRECT | 直接访问业务路由，不能证明菜单入口可用 |
| HYBRID | 先打开门户或控制台，再由辅助方法直达页面 |

### 1.3 退出风险

| 标记 | 含义 |
| --- | --- |
| N | 未发现跳过或静默放行逻辑 |
| P | 存在 `pytest.skip`，生产必跑时可能不失败 |
| S | 存在软通过：控件、数据或详情缺失时继续执行，或断言允许列表/空态代替目标对象 |

### 1.4 浏览器健康监控

`Health=Y` 表示交互期间已经统一监听 `console.error`、`pageerror`、404 和 5xx。
`Health=N` 表示主要依赖页面文案或 URL 断言，仍可能漏掉接口为 200 但前端渲染失败的情况。

### 4.1 生产执行分类基线

本分类决定用例在生产发布中的责任，不直接复用现有 `smoke` 标记。标记重构完成前，
`smoke and readonly` 仍会按当前范围收集用例，但发布结论应按以下四类解释。

| 分类 | 数量 | 执行责任 | 结果口径 |
| --- | ---: | --- | --- |
| Mandatory | 7 | 每次发布必须真实执行 | 只接受 `PASSED`；入口、前置数据、动作或断言缺失均为 `FAILED`，禁止 `skip` |
| Conditional | 35 | 满足已登记的角色、配置或数据前置条件时执行 | 满足条件后只接受 `PASSED/FAILED`；条件不满足记为 `NOT_APPLICABLE`，不得计入通过数 |
| Probe | 2 | 独立非阻断探查 | 发现问题必须在探查报告中显示为失败，不计入 Mandatory 通过率 |
| Controlled Write | 0 | 当前 44 条无写入用例 | 写入用例必须通过独立命令和显式授权执行 |

### 4.2 严格结果判定标准

#### 4.2.1 所有真实执行用例的五类证据

一条用例只有同时满足以下证据才可标记为 `PASSED`：

1. **前置条件证据**：环境、租户、账号、入口和测试数据与资产登记一致；不得临时使用“首条数据”替代指定业务对象，除非该策略已明确登记。
2. **动作发生证据**：目标元素可见且可交互，点击、输入或 Tab 切换确实发生；不得在找不到控件时记录日志后继续。
3. **状态变化证据**：动作后必须出现可验证变化，例如 URL/域名、活动 Tab、抽屉、弹窗、树、表格或目标字段状态改变。
4. **业务对象证据**：详情类用例必须证明进入目标对象并验证至少一个唯一标识和关键字段；“列表标题”“暂无数据”和通用页面文案不能替代详情证据。
5. **健康证据**：目标交互期间无错误页、`console.error`、未捕获 `pageerror`、404/5xx，也无关键接口的业务失败响应。

健康证据必须覆盖 HTTP 200 但 JSON 载荷失败的情况。对于目标动作触发的关键接口，除 HTTP 状态外还要校验业务码、
成功标志或有效数据结构；例如接口返回 `{"code": 50000, "message": "系统繁忙，请稍后再试"}` 时必须失败，不能因 HTTP 为 200 而放行。

#### 4.2.2 分类结果规则

| 分类 | 允许结果 | 禁止行为 |
| --- | --- | --- |
| Mandatory | `PASSED`、`FAILED` | `skip`、`xfail`、捕获异常后继续、入口缺失软通过、以空态代替目标对象 |
| Conditional | `PASSED`、`FAILED`、结构化 `NOT_APPLICABLE` | 运行到一半后因定位失败转为跳过；未登记前置条件的临时跳过 |
| Probe | 独立报告中的 `PASSED`、`FAILED`、`NOT_OBSERVED` | 把探查通过数合并到 Mandatory 通过率；用 `xfail` 隐藏新缺陷 |
| Controlled Write | 显式执行后的 `PASSED`、`FAILED`，或未授权时不收集 | 默认生产命令收集、操作非白名单数据、无唯一运行标识、无结果核验 |

#### 4.2.3 Mandatory 发布门禁

- Mandatory 任意一条未执行、跳过或失败，生产控制台门禁均为 `NO-GO`。
- Mandatory 用例必须沿用户可见 UI 路径执行；直链只能作为独立探活证据，不能替代入口链路。
- 每个 L2~L5 动作必须接入浏览器健康监控，并在动作前启动、页面稳定后停止。
- 健康监控忽略项必须是带原因、URL/错误模式和失效日期的显式白名单，禁止宽泛忽略整个接口或整个域名。

#### 4.2.4 Conditional 前置条件契约

- 条件必须在测试执行前完成判断，不能在点击或断言失败后再降级为不适用。
- 条件记录至少包含：条件类型、期望值、实际值、关联资产 ID 和责任人可识别的业务说明。
- 报告单独统计 `PASSED`、`FAILED` 和 `NOT_APPLICABLE`；通过率分母只包含本次条件满足并真实执行的用例。
- 连续两个发布周期出现 `NOT_APPLICABLE` 的用例必须复审：固定前置条件、降级为 Probe，或从当前租户范围移除。

#### 4.2.5 Controlled Write 安全契约

- 必须同时满足显式 marker、环境开关和数据白名单，生产环境不得仅依赖一个布尔开关放行。
- 测试数据必须带环境和运行唯一标识；删除、审批、提交等动作只能作用于本次创建或明确授权的对象。
- 写入前记录目标对象唯一标识，写入后验证服务端结果和 UI 回显；可清理的数据必须执行精确清理并验证。
- 禁止模糊搜索后操作首条数据、批量操作、跨应用域操作以及对非测试专用数据执行删除或状态流转。

## 7. 建议实施顺序

本矩阵审核通过后再开始代码阶段，每轮只处理一个边界明确的批次：

1. 先治理共性门禁：生产 `skip` 策略、健康监控、动作发生证据，不新增业务范围。
2. 权限管理补齐：角色成员、数据权限、编辑确认前探查，再覆盖登录/用户/租户管理。
3. 资源管理补齐：先从左侧菜单建立真实路径，再覆盖数据资源管理的列表、详情和只读 Tab。
4. 系统配置按 6 个二级菜单逐页实施，每次 2 个页面。
5. 评价、计量、运维、运营按菜单组分批实施。
6. 订阅、订单、审批、工单把已有候选稳定化，消除软通过后再晋级生产默认。
7. 最后建立 L5 确认前操作矩阵；真实写入继续放在独立显式套件。

## 9. 公共框架升级设计（Step 3）

本节定义实现边界。Step 4 首批只改造 7 条 Mandatory，用实际运行验证公共能力后，
再分批迁移 Conditional 和 Probe，避免一次性重写 44 条用例。

### 9.1 执行责任与功能属性分离

现有 `smoke`、`readonly`、`write`、`destructive` 描述测试功能和风险，不能表达发布责任。
新增以下正交 marker：

| Marker | 用途 |
| --- | --- |
| `prod_mandatory` | 生产发布强制门禁，只允许通过或失败 |
| `prod_conditional` | 生产条件用例，允许结构化 `NOT_APPLICABLE` |
| `prod_probe` | 生产非阻断探查，单独执行和统计 |
| `controlled_write` | 生产受控写入，必须同时具备 `write` 或 `destructive` |

迁移期间 `python run_tests.py --env prod` 暂时保留现有 `smoke and readonly` 选择，新增显式参数：

```powershell
python run_tests.py --env prod --prod-suite mandatory
python run_tests.py --env prod --prod-suite conditional
python run_tests.py --env prod --prod-suite probe
python run_tests.py --env prod --prod-suite controlled-write
```

当门户、移动端和控制台的 Mandatory 全部完成分类与迁移后，再把生产默认选择切换为 `prod_mandatory and readonly`。

### 9.2 机器可读执行契约

新增 `test_assets/registry/prod_console_case_contracts.yaml`，以 44 个展开后的 Case ID 为粒度记录：

- `case_id`：矩阵中的稳定业务 ID；
- `node_id`：对应 pytest 节点或参数化节点模式；
- `classification`：Mandatory、Conditional、Probe 或 Controlled Write；
- `entry_type`：UI、DIRECT 或 HYBRID；
- `max_depth`：L0~L6；
- `prerequisites`：角色、模块配置和业务样本等前置条件；
- `expected_state`：动作后 URL、Tab、弹窗、抽屉或业务对象证据；
- `critical_api_patterns`：本动作必须检查的关键接口 URL 模式；
- `owner_note`：业务人员可识别的适用范围和数据说明。

该文件作为控制台执行分类的单一机器事实来源；Markdown 矩阵保留为评审视图。

### 9.3 前置条件与结果模型

新增 `core/execution_contract.py`，负责加载契约和判断前置条件：

- Mandatory 前置条件不满足时抛出失败，不允许转成 `skip`；
- Conditional 只允许在测试动作开始前产生 `NOT_APPLICABLE[case_id][reason]`；
- 测试动作开始后出现入口缺失、定位失败或数据消失，一律记为失败；
- Probe 未发现目标入口时记为 `NOT_OBSERVED`，不伪装成通过；
- Controlled Write 未满足授权条件时不收集，满足条件后必须执行完整结果核验。

pytest 报告增加分类统计，并生成 `reports/prod-console-contract-summary.json`，至少包含：
Mandatory 通过/失败/未执行、Conditional 通过/失败/不适用、Probe 发现结果和 Controlled Write 执行范围。

### 9.4 动作与状态变化证据

新增轻量 `core/interaction_evidence.py`，不把业务流程封装成通用大函数，只提供可复用检查点：

- `require_actionable(locator, action_name)`：元素必须可见、可用且可交互；
- `click_and_expect(locator, expectation, action_name)`：点击后必须满足调用方提供的 Web-First 期望；
- `require_surface_change(before, after, action_name)`：验证 URL、活动 Tab、弹窗、抽屉或内容区发生目标变化；
- `require_business_identity(locator, expected, object_name)`：验证详情对象唯一标识；
- 所有失败信息携带 Case ID、动作名、当前 URL 和预期状态。

业务定位器和期望状态仍放在对应 POM 中，测试层只编排意图，避免形成新的万能工具类。

### 9.5 浏览器健康监控升级

扩展 `core/browser_health.py`：

1. 从单 Page 监听提升为 Context 范围，自动覆盖弹窗和新开页面；
2. 增加 `requestfailed`，保留 `console.error`、`pageerror`、404 和 5xx；
3. 只对契约声明的关键 XHR/Fetch 且响应为 JSON 的接口读取载荷，避免扫描图片、文件和无关大响应；
4. 支持按接口声明成功业务码、成功标志或必需数据结构；HTTP 200 但业务失败必须记录为 `business_response`；
5. 忽略规则使用精确 URL/错误模式、原因和失效日期，过期规则使校验失败；
6. `assert_healthy()` 输出请求 URL、HTTP 状态、业务码、消息和触发动作，便于直接定位问题。

业务响应规则不使用全局的“非 0 即失败”猜测，每个关键接口由 Case 契约声明，防止不同后台编码约定造成误报。

### 9.6 UI 路径与直链探活分离

- Mandatory POM 禁止调用 `navigate_with_fallback()`，也禁止菜单失败后直达路由；
- UI 路径必须从控制台公开入口逐级点击，并验证每一层可见状态；
- DIRECT 路径保留为 Probe，验证路由和页面服务是否存活，但不再计作菜单覆盖；
- HYBRID 必须明确哪一段是 UI、哪一段是初始化辅助，报告中不能简写成完整用户路径；
- 导航结果记录实际入口类型，契约为 UI 但运行结果为 DIRECT 时直接失败。

### 9.7 等待和异常处理门禁

- 新增或改造的 Mandatory 代码禁止 `time.sleep()` 和 `page.wait_for_timeout()`；
- 使用 Playwright locator 自动等待、`expect()`、URL、活动 Tab、遮罩消失或目标响应完成作为等待条件；
- 禁止 `except Exception: pass/continue`；确需兼容多个 UI 形态时，只捕获预期的 Playwright 超时并在所有候选失败后抛出包含证据的异常；
- Mandatory 测试和其直接 POM 中禁止调用 `pytest.skip()`；Conditional 的不适用只能由前置条件层产生。

### 9.8 契约验证器

新增 `tools/validate_prod_console_contracts.py`，在提交前检查：

- 44 个 Case ID 是否全部且仅登记一次；
- pytest 实际收集节点是否能与契约匹配；
- 每个 Case 是否恰好属于一个执行分类；
- Mandatory 是否同时为 `readonly`、`entry_type: UI/HYBRID` 且不存在 DIRECT 兜底；
- Controlled Write 是否具备写入 marker、授权变量和数据白名单字段；
- Mandatory 测试函数是否存在显式 `pytest.skip`、`xfail` 或固定等待；
- 契约中的关键接口规则、预期状态和前置条件是否完整。

现有 `tools/validate_ui_assets.py` 继续负责资产登记合法性，新验证器只负责生产控制台执行契约，职责不混合。
