# UI 自动化资产治理规范

本文档定义 `cscec-ui-autotest` 工程的通用 UI 自动化资产治理规则。它适用于所有新需求、已上线历史功能、缺陷回归、生产 smoke 和后续新增模块，不绑定任何单次迭代或单个需求。

本工程定位为纯 UI 自动化工程。所有纳入本工程的用例，都应通过前端页面操作和 UI 可观察证据完成验证；不在本工程内调用后端接口作为主要断言方式。若某个场景更适合接口测试，应记录为“非 UI 工程承接”，由独立 API 测试工程覆盖。

## 1. 资产来源

UI 自动化资产可以来自以下来源：

| 来源 | 说明 | 典型入口 |
| --- | --- | --- |
| 新需求黑盒测试 | 迭代测试阶段由需求测试用例沉淀而来 | `test-case-generator` 产出的 `详细测试用例数据.json` |
| 已上线历史功能回归 | 针对生产稳定功能补充自动化回归 | 人工回归清单、历史发布范围、核心业务路径 |
| 缺陷回归 | 针对已修复问题沉淀防回归用例 | 缺陷单、线上问题复盘、回归验证记录 |
| 生产 smoke | 上线后默认可安全执行的只读核心路径 | 登录、首页、核心入口、只读查询 |
| 可行性探查 | 入口、定位、数据或断言尚不稳定的候选路径 | 手工探查记录、临时实验用例 |

不同来源的用例最终都应进入同一套资产生命周期和登记规则。

## 2. 资产目录

| 路径 | 用途 |
| --- | --- |
| `test_assets/incoming/` | 新需求或批量候选资产的临时清单，等待人工评审和分类 |
| `test_assets/registry/ui_case_assets.yaml` | 已登记资产池，记录状态、测试路径、marker、环境策略和验证证据 |
| `test_assets/schema/ui-case-asset.schema.json` | 资产登记结构约束 |
| `docs/ui-asset-governance.md` | 本治理规范 |

原则上，单次迭代的候选数量、模块分布、具体用例标题不写死在本治理规范里；这些信息保存在对应的 `incoming` 文件或后续统计报表中。

## 3. 归属分类

所有候选用例先做归属判断，再决定是否实施。

| 归属 | 含义 | 本工程动作 |
| --- | --- | --- |
| UI 自动化纳入 | UI 价值明确，入口稳定，断言可从页面稳定读取 | 实施 Page Object、测试数据和 pytest 用例 |
| UI 暂缓/待稳定 | 有 UI 价值，但入口、数据、提示、错误行、表格或下载结果未确认稳定 | 先登记，做可行性探查，不直接批量自动化 |
| 非 UI 工程承接 | 本质更适合接口、数据、性能或批处理验证 | 本工程不实现；必要时交给独立工程 |
| 人工保留 | 强依赖人工判断、环境不稳定、自动化收益低或执行风险高 | 本工程不实现，仅保留说明 |

`api_preferred` 只表示“不适合在本 UI 工程实现”，不表示本工程要写 API 调用或接口断言。

## 4. UI 纳入标准

候选用例进入 UI 自动化实施前，必须满足：

- 有明确页面入口、菜单路径或稳定 URL。
- 有至少一个稳定的 UI 断言点。
- 不依赖后端接口作为主要通过标准。
- 测试数据可以唯一化、复用、临时生成或清理。
- 失败后能判断是框架、定位、环境、数据还是业务问题。
- 写入类用例仅默认在 UAT/PRE 执行，不进入 PROD 默认集合。

可接受的 UI 证据包括：

- 页面文本、Toast、通知、弹窗、警告。
- 按钮可见性、禁用状态、权限显隐。
- 表格行、空态、分页、筛选结果、详情页字段。
- 上传/下载控件状态。
- 下载文件内容，只要文件来自前端操作且解析过程稳定。
- 前端搜索、筛选、排序后展示的数据。

## 5. 数据规则类策略

数据规则类用例包括但不限于：

- 必填字段校验。
- 重复判定。
- 字段组合规则。
- 多行错误提示。
- 大小写敏感性。
- 导入前后数据一致性。
- 批量数据边界。

这类用例默认先进入 **UI 暂缓/待稳定**，不因 P0 或业务重要就直接强行自动化。只有完成 UI 证据可行性探查，并确认页面上能稳定读取错误提示、错误行、表格结果、按钮状态、下载文件或详情页字段后，才允许晋级为 **UI 自动化纳入**。

如果某条数据规则只能通过数据库或后端接口稳定验证，则本工程不实现；可记录为 `api_preferred` 或人工保留。

## 6. 生命周期

| 生命周期 | 含义 |
| --- | --- |
| `new_requirement` | 来自新需求阶段，尚未完成自动化判断或落地 |
| `candidate` | 已确认有 UI 自动化价值，但未实施或未稳定 |
| `uat_automated` | 已在 UAT 完成自动化并有通过证据 |
| `pre_verified` | 已在 PRE 完成验证，具备上线前回归价值 |
| `prod_regression` | 已上线后沉淀为生产回归资产 |
| `manual_only` | 本工程不自动化，保留人工覆盖 |
| `api_preferred` | 本 UI 工程不做，必要时交给独立 API 测试工程 |
| `deprecated` | 需求下线、入口失效或资产不再维护 |

生命周期描述资产所处业务流转阶段，不等同于测试是否能运行。

## 7. 自动化状态

| 状态 | 含义 |
| --- | --- |
| `candidate` | 待评估或待实施 |
| `automated` | 已有可运行自动化用例 |
| `needs_stabilization` | 已有方向或用例，但入口、定位、数据或环境不稳定 |
| `manual_only` | 保留人工测试 |
| `api_preferred` | 不在本工程实现 |
| `deprecated` | 不再维护 |

自动化状态描述工程实现状态，可以和生命周期组合使用。例如：`lifecycle=candidate` 且 `automation_status=needs_stabilization` 表示有价值但暂不稳定。

## 8. 晋级规则

### 8.1 候选到 UAT 自动化

候选用例晋级为 `uat_automated` 前，必须满足：

- 已有 pytest 用例路径。
- 已登记 Page Object 或测试辅助能力。
- 已设置 marker 和环境策略。
- UAT 至少一次通过。
- `evidence.uat` 记录执行命令和结果。

### 8.2 UAT 到 PRE

用例晋级为 `pre_verified` 前，必须满足：

- UAT 通过记录仍有效。
- PRE 入口、权限、页面结构和测试数据策略可复用。
- PRE 至少一次通过。
- `evidence.pre` 记录执行命令和结果。

### 8.3 PRE 到生产回归

用例晋级为 `prod_regression` 前，必须满足：

- 对应需求或功能已上线。
- PRE 已验证通过。
- 用例适合长期维护。
- 生产执行策略明确。

只有稳定只读路径才允许进入 PROD 默认集合。写入、上传、导入、审批、删除等用例可以保留为生产显式执行资产，但必须设置 `prod_default: false`。

## 9. 降级规则

出现以下情况时，应降级或移出自动化实施范围：

- 页面入口频繁变化，无法稳定定位。
- 核心断言只能依赖后端接口，本工程无法通过 UI 可靠观察。
- 测试数据不可控，执行后污染环境或影响其他测试。
- 用例强依赖人工判断、第三方系统、长耗时或强时序。
- 功能下线、入口移除或业务规则变更。
- 用例长期失败且没有稳定修复价值。

降级目标应明确为 `needs_stabilization`、`manual_only`、`api_preferred` 或 `deprecated`。

## 10. 环境策略

| 环境 | 默认策略 |
| --- | --- |
| UAT | 允许写入、上传、保存、导入、审批等测试 |
| PRE | 允许上线前验收和回归验证 |
| PROD | 默认只跑 `smoke + readonly` |

PROD 下如果显式指定写入类 marker/path，可以执行，但资产登记中必须保留 `prod_default: false`。生产默认集合不能因为单条用例重要就绕过只读原则。

### 10.1 生产执行分层管理

生产环境的 UI 资产按“是否改变业务状态”分层管理，避免只读走查、可增删改、破坏性动作混跑。

| 类别 | 典型动作 | 资产标记 / 约束 | 默认执行方式 |
| --- | --- | --- | --- |
| 只读走查 | 页面打开、菜单展开、详情查看、搜索填充清空、路由跳转、hover 展示 | `readonly` + `smoke`；`prod_default=true`；`prod_explicit=true` | 进入 `python run_tests.py --env prod` 默认集合 |
| 可增删改 | 新增、编辑、上传、导入、保存、提交、确认、启停用前置动作 | `write`；`prod_default=false`；`prod_explicit=true` | 仅显式执行，必须限定路径/用例组和数据边界 |
| 破坏性动作 | 删除、撤回、作废、不可逆审批、真实清理 | `destructive`；`prod_default=false`；`prod_explicit=true` | 仅少量受控资产，执行前需再次确认回滚/清理方案 |

管理要求：

- 只读走查只覆盖“打开即验证”的路径，不进入提交、保存、删除确认、真正导入等动作。
- 写入类用例允许在 UAT/PRE/PROD 显式执行，但生产默认集合必须排除。
- 数据重复校验类用例保持必要重复，不做唯一化；只有“写入型种子 / 落库准备”场景才生成运行时唯一后缀。
- 生产写入类资产必须在 `notes` 或 `evidence` 中写清：目标域/租户、数据范围、是否可重复执行、是否需要清理。
- 破坏性用例如需进入生产，必须单独评审，不和普通写入用例混跑。

推荐执行口径：

- `python run_tests.py --env prod`：只跑 `smoke and readonly`
- `python run_tests.py --env prod -m write`：仅显式写入类
- `python run_tests.py --env prod -m destructive`：仅受控破坏类，默认不建议批量执行

## 11. Marker 规则

基础 marker：

- `readonly`：不产生业务写入或状态变更。
- `write`：上传、保存、提交、导入、新增、编辑等写入类操作。
- `destructive`：删除、撤回、作废、不可逆审批流转等高风险操作。
- `smoke`：稳定核心只读路径。
- `regression`：回归范围。
- `e2e`：完整业务链路。

模块 marker 按工程实际模块扩展，例如：

- `login`
- `console`
- `doccenter`
- `ops`
- `dataresources`

分类原则：

- 上传但未真正导入、未写入业务数据的用例，仍标记为 `write`，不标记为 `readonly`。
- 只有删除、作废、撤回、不可逆审批等高风险状态变化才标记为 `destructive`。
- 数据规则类用例默认不因 P0 自动进入 `smoke`。
- `smoke` 应优先保持少量、稳定、只读、核心。

## 12. 新需求流转流程

1. 使用原始 `test-case-generator` 生成 `详细测试用例数据.json`。
2. 使用本工程适配器生成 `test_assets/incoming/<需求名>.ui-assets.yaml`。
3. 人工按本规范评审候选用例，先归类为 UI 自动化纳入、UI 暂缓/待稳定、非 UI 工程承接或人工保留。
4. 对 UI 暂缓/待稳定的数据规则类用例，先做页面可行性探查，不直接写自动化用例。
5. 探查通过后实施 Page Object、测试数据生成和 pytest 用例。
6. UAT 通过后写入 `registry/ui_case_assets.yaml`，记录 test path、marker、环境策略和 evidence。
7. PRE 验证通过后更新为 `pre_verified`。
8. 需求上线后，只读稳定路径可沉淀为 `prod_regression`；写入类保留显式执行策略。

## 13. 历史回归流转流程

历史回归不要求来自 `test-case-generator`，但必须遵守同一套资产登记规则。

优先级建议：

1. 已在 PROD 可安全执行的 `smoke + readonly` 路径。
2. UAT/PRE 中稳定的核心写入路径。
3. 历史问题高发、页面证据稳定、测试数据可控的路径。
4. 入口不稳定或强依赖人工判断的路径先登记为 `needs_stabilization` 或 `manual_only`。

历史回归资产必须记录来源、测试路径、marker、环境策略和验证证据。

## 14. 评审清单

每条资产进入实施前，按以下问题评审：

- 这个用例是否必须通过 UI 才能体现价值？
- 页面入口是否稳定？
- 断言是否能从 UI 可见文本、按钮、表格、弹窗、文件中读取？
- 数据是否能唯一化、复用或清理？
- 是否会写入、上传、导入或改变业务状态？
- 是否适合 UAT/PRE？
- 是否禁止进入 PROD 默认集合？
- 失败后能否判断是框架、定位、环境、数据还是业务问题？
- 是否需要先做可行性探查？

评审结论必须落到一个明确状态：`candidate`、`uat_automated`、`needs_stabilization`、`manual_only`、`api_preferred` 或 `deprecated`。

## 15. 快照与报表原则

资产数量、候选数量、模块分布、某次迭代完成情况属于状态数据，不属于治理规则。

状态数据应优先通过以下方式维护：

- `test_assets/incoming/<需求名>.ui-assets.yaml`
- `test_assets/registry/ui_case_assets.yaml`
- 后续资产统计或报表脚本

治理文档只记录长期规则，不写死某次需求的候选数量或模块明细。
